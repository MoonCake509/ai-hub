## NET-01 — Качественный маршрут связи между ноутбуком и сервером

**Статус:** backlog, не блокирует проект (внутри дома работаем по LAN).
**Приоритет:** средний. **Напоминание:** вернуться после этапа LiteLLM/hub-agent.

### Симптомы

1. Tailscale между ноутбуком (`desktop-bhmjn55`, 100.108.134.99) и сервером
   (`win-v76qc2g60q1`, 100.104.134.6) поднимается только через DERP-релей
   (~150 мс, `direct connection not established`), хотя обе машины в одной сети
   192.168.31.0/24 и ходят друг к другу по ICMP за 2–8 мс.
2. Ноутбук **не может подключиться к серверам Tailscale без включённого VPN** (happ):
   при исключении Tailscale из туннеля ломается control plane
   (`fetch control key … connection aborted`, состояние `NoState`), потому что
   happ подменяет DNS на фейковые адреса (`192.200.0.105`, `172.19.0.2`),
   а трафик после исключения идёт мимо туннеля на эти адреса.
3. Крупные TLS-загрузки на сервере рвутся: `tls: bad record MAC` (docker pull падает
   на слое ~16 МБ), обрезанные MSI/rootfs (33.8 МБ вместо 350 МБ, 277 МБ вместо 340 МБ).
   Рабочий обход — докачка `curl -C -`; `docker pull` так не умеет.

### Что проверено

- `tailscale debug netmap` на ноутбуке: endpoint сервера `192.168.31.95:41641` **есть**.
- Сервер → ноутбук: `pong via 192.168.31.152:41641 in 2ms` (прямой канал работает).
- Обновление Tailscale 1.102.4 → 1.104.5, перезапуски службы, `debug rebind`,
  `debug rotate-disco-key` — прямой канал не появился.
- Фаервол на сервере выключен полностью, `tailscaled` слушает `0.0.0.0:41641`.
- UDP-проба ноутбук → сервер (`:45678`) доходит с корректным адресом источника.
- MTU happ-туннеля снижен до 1400 — проверка в процессе.
- Пинг с DF до 1472 байт проходит, то есть чёрной дыры MTU на ICMP нет.

### Гипотеза

Пользовательский стек happ-xray (TUN + подмена DNS + перехват TLS) ломает
крупные TLS-потоки и мешает magicsock выбрать прямой путь: пакеты уходят
через виртуальный интерфейс, а не через физический Wi-Fi.

### Варианты (в порядке проверки)

1. **happ как SOCKS-прокси, без TUN.** Основной маршрут — напрямую через роутер,
   happ используется только теми приложениями, которым он реально нужен (Telegram).
   Даёт: прямой путь для Tailscale, целые TLS-загрузки, нормальный MTU.
2. **Исключение с исправлением DNS.** Если оставлять TUN: помимо исключения
   Tailscale нужно отключить подмену DNS для `*.tailscale.com` и
   `controlplane.tailscale.com`, иначе control plane не поднимется.
3. **Свой координационный сервер** (headscale) или собственный DERP — убирает
   зависимость от доступности controlplane.tailscale.com, но не лечит TLS-обрывы.
4. **WireGuard напрямую** между узлами — самый простой прямой канал, без координатора.

### Критерий готовности

- `tailscale ping` (или аналог) между ноутбуком и сервером: прямой путь, < 10 мс.
- `docker pull` образа > 500 МБ без обрывов.
- Telegram на сервере продолжает работать (через прокси, не через TUN).
