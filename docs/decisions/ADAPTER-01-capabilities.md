# ADAPTER-01: матрица возможностей и preflight

**Статус:** принято 2026-11-10.

## Проблема

Каталог агентов заявлял возможности списком моделей и парой полей (`filesystem_access`, `model_selection`). Из этого нельзя было понять, что канал действительно умеет: работает ли он в каталоге проекта, запускает ли команды, отдаёт ли usage, умеет ли остановиться. Неподдержанный режим выбирался молча — пользователь узнавал об этом уже из результата.

## Решение

1. **Восемь возможностей объявлены явно** для каждого агента: `text`, `patch`, `workdir`, `commands`, `usage`, `streaming`, `stop`, `output_control`. Наследование: агент → профиль → модель, побеждает более конкретный уровень.
2. **У каждой возможности есть источник**: `catalog` (заявлено), `fixture:<имя>` (подтверждено отдельной проверкой), `unknown`. Выключенная возможность обязана иметь причину; тест каталога падает, если причины нет.
3. **Необъявленное — выключено.** Отсутствие поля не означает «наверное работает»: оно даёт `supported: false` с причиной «не подтверждено» и `evidence: unknown`.
4. **Preflight до очереди.** `POST /agents/{id}/run` принимает `needs` — список требуемых возможностей. Неизвестное имя → `409 unknown_capability`; недоступная возможность → `409 capability_unsupported` с причиной по каждой. Молчаливого отката к «как получится» нет.
5. **Модель — параметр одного запуска.** Codex получает `-m <model>`, Hermes — `--provider/--model`; глобальные конфиги клиентов не переписываются, параллельные профили не перетирают друг друга.
6. **Незапрошенная модель не выдумывается.** `model` остаётся пустым (`null`), а `default_model` показывает, что канал применит сам. Если канал не раскрывает фактическую модель, поле эффективной модели остаётся пустым.
7. **UI показывает границы.** Под селектором модели выводится «Доступно: … · выключено: …», в подсказке — причина по каждой выключенной возможности.

## API

- `GET /agents/{agent_id}/capabilities` — матрица по всем профилям и моделям.
- `GET /agents/{agent_id}/capabilities?profile=&model=` — конкретная комбинация.
- `POST /agents/{agent_id}/run` с `needs: [...]`.
- `GET /agent-profiles/{agent_id}` теперь содержит `capabilities`.

## Проверено

- `tests/test_adapter01_capabilities.py` — 17 проверок в образе хаба: полнота каталога, причины у выключенного, наследование уровней, неизвестный профиль/модель, preflight-отказы и пропуск поддержанной комбинации.
- `tests/test_adapter01_bridge.py` — 6 проверок на Windows-хосте: модель передаётся флагом запуска, конфиги клиентов не меняются (сверка хешей), параллельные профили не перетираются, OpenClaw отказывает вместо тихого игнорирования, неизвестная модель отвергается.
- Живой прод: `GET /agents/codex/capabilities` отдаёт 10 моделей с поддержкой `text,patch,workdir,commands,usage,output_control` и выключенными `streaming,stop`; `needs=["workdir"]` для `llm-server` → `409 capability_unsupported`; `needs=["telepathy"]` → `409 unknown_capability`.

## Отклонено

- Выводить возможности из наличия модели в каталоге — каталог не доказательство исполнения.
- Разрешать запуск с предупреждением вместо отказа — предупреждение теряется в потоке.
- Писать выбранную модель в глобальный конфиг клиента — ломает параллельные профили.
- Заполнять `effective_model` первой моделью профиля — это догадка, а не факт.
