# CORE-01. Gate протокола и outbox: кто имеет право арендовать задание

**Дата:** 2026-11-10 · **Статус:** принято и реализовано

## Вопрос

`GET /bridge/jobs` отдавал задание любому клиенту, который знал адрес и токен. Воркер v1
(до outbox и до контракта heartbeat) мог арендовать задание, поставленное для v2, и «потерять»
его при первом падении: результата нет, аренда истекает, задание становится `unknown`, хотя
никто его не исполнял. Одновременно воркеры считали интервал подтверждения как
`max(20, lease // 3)`, поэтому на стенде с арендой 3 с первое подтверждение приходило на
20-й секунде — то есть уже после истечения, при живом исполнителе.

## Решение

**1. Версия протокола — обязательный параметр аренды.** `GET /bridge/jobs` принимает
`protocol=<int>`. Хаб обслуживает только версии из `SUPPORTED = (2,)`; отсутствие параметра
трактуется как legacy-клиент v1. Отказ — явный `426 Upgrade Required` с телом
`{detail, supported: [2], current: 2, heartbeat_interval_s, job: null}`, а не пустая очередь:
иначе старый воркер бесконечно опрашивал бы хаб и выглядел живым, никогда не получая заданий.

**2. Задание помнит свой протокол.** `aihub.jobs.protocol` (по умолчанию 2) — минимальная
версия клиента, которой можно это задание арендовать. Аренда фильтрует `protocol <= :client`.
`aihub.job_attempts.protocol` — версия, на которой задание реально взяли; heartbeat сверяет
её с протоколом задания (`409` при расхождении). Старое задание можно пометить `protocol = 1`
и отдать legacy-клиенту, но новые задания так не создаются.

**3. Интервал подтверждения задаёт хаб.** `heartbeat_interval = clamp(lease // 3, 1..60)`
(`hub/app/protocol.py`) и приходит в ответе на аренду. Воркер не имеет права ждать дольше
трети аренды: `attempt_heartbeat_interval(lease, advertised)` берёт значение хаба, но
урезает его до `lease // 3` (минимум 1 с). При `LEASE_SECONDS=3` это 1 с вместо прежних 20 с.

**4. Проверка интервала относительно аренды видна в диагностике.** Воркер сообщает свой
интервал (`hb_interval_s`) в heartbeat; хаб пишет его в `aihub.workers.hb_interval_s`, считает
`lease_risk` и отдаёт в `POST /bridge/heartbeat` и `GET /workers`. Причина формулируется
словами («интервал подтверждения 60 с не короче аренды 3 с: попытка истечёт между
подтверждениями»), а не выводится из молчания.

**5. Durable ack остаётся строгим.** Воркер удаляет файл outbox только при
`200 + ok=true + recorded=true + outcome ∈ {applied, duplicate, late, stale}`; при `404/409`,
сетевой ошибке или невалидном JSON файл остаётся и повторяется позже. Хаб идемпотентен по
`attempt_id`: повторная доставка даёт `duplicate` и не создаёт новой попытки; поздний
результат (`late`) сохраняется в `late_results` и не переписывает статус задания.

## Границы

- Legacy-клиент v1 полностью отсечён: если такой воркер ещё где-то запущен, он получит `426`
  и запишет это в лог, но заданий не возьмёт. Совместимость «умереть тихо» сознательно не
  делается.
- Версия протокола не заменяет авторизацию: токен проверяется как раньше.
- `lease_risk` — диагностика настройки, а не блокировка: хаб не отказывает в heartbeat,
  потому что иначе живая попытка гарантированно терялась бы.

## Проверено

- Юнит хаба: 8 проверок (`tests/test_core01_protocol.py`) — разбор версии, отказ legacy/чужой/
  мусорной версии, интервал для аренды 1–9 с и 300/7200 с, `lease_risk` на границе половины.
- Юнит воркеров: 4 проверки (`tests/test_core01_worker_interval.py`, оба файла воркеров
  загружаются как есть) — интервал 60 с при аренде 300 с, 1 с при аренде 3 с даже если хаб
  прислал 60, наличие `protocol=` и `hb_interval_s` в опросе.
- Живой контракт стенда: 22 проверки (`tests/test_core01_api.py`) — `426` без версии,
  `protocol=1`, `protocol=abc`; аренда с `protocol=2` отдаёт `protocol: 2` и интервал короче
  аренды; второй клиент не получает то же задание; heartbeat принят и возвращает интервал;
  слишком длинный интервал помечен риском; результат применён, повтор — `duplicate`, у задания
  одна попытка, статус `succeeded`.
- Живая проверка короткой аренды: 9 проверок (`tests/test_core01_short_lease.py`) на стенде с
  `LEASE_SECONDS=3` и уборкой каждые 2 с — через 8 с живых heartbeat задание и попытка всё ещё
  `running`, результат применяется как актуальный; контрольное задание без heartbeat честно
  становится `unknown` (доказывает, что уборка аренд работает и выживание — заслуга heartbeat).
- Полный контракт стенда: 47 проверок, 0 падений.
