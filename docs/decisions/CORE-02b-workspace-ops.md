# CORE-02b. Операции рабочего пространства и выбор задания под свободный checkout

Дата: 2026-11-10. Статус: принято, реализовано, проверено живым прогоном.

## Решения

1. **Операции — фиксированный набор, а не присланный код.** Разрешены семь операций: `inspect`, `snapshot`, `list_files`, `read_files`, `apply_patch`, `run_checks`, `package`. Аргументы проверяются по схеме, лишние поля отвергаются. Модель может попросить операцию и её параметры, но не может прислать команду оболочки или свой скрипт.
2. **Доставка — существующий канал заданий.** В `aihub.jobs` добавлено `kind` (default `agent`). Control-задание имеет `kind='workspace'`, служебного агента `workspace` и JSON-конверт в `prompt`. Отдельного механизма доставки нет: аренда, attempts, outbox, heartbeat и receipts работают те же.
3. **Ворота по возможностям, а не по версии протокола.** Воркер объявляет `capabilities.kinds` и `capabilities.workspace_ops` в heartbeat; хаб ставит задание только на host, где операция объявлена, иначе `unsupported_op`. Воркер без модуля операций просто не объявляет `workspace` и такие задания не арендует. Старый поллер control-задание не получит.
4. **Корни только из проектов этого host.** `root` обязан лежать внутри `projects.workdir` того же `host_id`; путь канонизируется средствами целевой ОС (`ntpath` для буквы диска), сравнение без учёта регистра и разделителей. Выход через `..`, абсолютная подстановка и симлинк/junction наружу отвергаются и на хабе, и на воркере.
5. **Секреты и служебное — вне операций.** `.env*`, ключи, dumps, `.git`, `node_modules`, `.venv`, `outbox`, `models`, `.ssh` не читаются, не листятся, не попадают в снимок и бандл. Отказ выдаётся кодом `denied_path` до постановки задания.
6. **Модифицирующее — с ключом и digest.** `apply_patch` требует `base_tree_digest` (из `inspect`) и `preimage_sha256` для существующих файлов; `tree_digest` включает хеш содержимого, поэтому две одинаковые по структуре копии различаются. Повтор с тем же `idempotency_key` возвращает прежнее задание, а воркер дополнительно хранит receipt по `job_id`: повторная доставка не применяет патч второй раз.
7. **Чтение идемпотентным не считается.** `read_files`/`list_files`/`inspect` с ключом по умолчанию не дедуплицируются: иначе клиент получал бы старое содержимое после изменения файла. `snapshot` получает ключ с секундной меткой — повтор запроса не плодит копии, а новый запуск видит актуальное дерево.
8. **Проверки — в изолированной копии.** `run_checks` исполняет план из настроек проекта (`projects.settings.checks`) в каталоге снимка, а не в рабочем дереве. Команды берутся из доверенной конфигурации проекта, не из текста модели и не из аргументов операции.
9. **Снимок не трогает работу пользователя.** Копия делается в управляемый каталог (`%LOCALAPPDATA%\aihub\workspaces`), без stash/commit и без правок исходников. Незакоммиченные изменения пользователя остаются как есть; `apply_patch` защищён preimage и `base_tree_digest`.
10. **Честная выборка.** Аренда перебирает до 10 кандидатов очереди по FIFO и берёт первое задание, чей checkout свободен; занятый каталог больше не превращает очередь в пустой ответ. Задания, которые пишут только в управляемую область (`snapshot`, `package`, чтение), писательскую аренду не берут.

## Ограничения (следующие шаги)

- Изоляция тестового стенда от рабочего дерева (compose стенда монтирует `../hub/app`) — отдельный шаг; в этом прогоне не менялась.
- `workspace_host.py` стоит только на ноутбуке. Для `host_id=server` операции ответят `unsupported_op`, пока модуль не развёрнут на серверном воркере.
- `snapshot` копирует до 20 000 файлов / 200 МБ и не хранит инкрементальных дельт; старые снимки не чистятся автоматически.
- `run_checks` не ограничивает сетевой доступ и не подменяет окружение сверх каталога снимка; sandbox — задача FLOW/REL.
- Аренды CDP/CLI/модели по-прежнему не выдаются автоматически (это ADAPTER-01).
