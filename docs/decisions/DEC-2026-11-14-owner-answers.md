# DEC-2026-11-14: ответы владельца на разбор Qwen (6 претензий)

**Статус:** принято 2026-11-14. Источник вопросов — `docs/QWEN-REVIEW-2026-11-14.md`, раздел 5.

Эти ответы — входные требования для этапов 2–6 плана. Пункты, помеченные «открыто», ещё не решены и не должны реализовываться по догадке.

## Решения

1. **Codex на ноутбуке остаётся.** Единственный подтверждённый канал `patch`/`workdir`/`commands` не отключаем. Целевое состояние — перевод на серверный канал, но это отдельная задача после того, как серверный канал подтвердит `patch`/`commands` fixture-проверкой.
2. **Единица учёта расходов — токены.** Разрез: провайдер → модель → задача/роль → проект. Деньги и прайс не вводим. Сверка «сколько потратила модель/провайдер на задачу» идёт по `usage` попыток; каналы без `usage` помечаются «нет данных канала», оценка — «оценка», а не деньги.
3. **Enforcement лимитов — в backlog.** Считаем и показываем, но вызовы не блокируем. Жёсткий блок/очередь/fallback — отдельным решением позже.
4. **Qwen остаётся на подписке через CDP.** Thinking управляется через DOM-адаптер, не через API-ключ.
5. **Корень рабочих пространств — диск `R:`.** На `R:` создаётся единый workspace, внутри него проекты разбиваются по папкам. Конфиг `projects.root` переводится с `R:\Projects` на новый корень; уже созданные проекты переезжают с барьером «нет активных прогонов».
6. **Архивариус не удаляет.** Удаление запрещено; он формирует предложение («что убрать») и кладёт его в отчёт. Обязательный доступ — папка `map` проекта: в ней архивариус ведёт навигацию по проекту, чтобы агенты не искали файлы вслепую. Перемещение/переименование/карантин — разрешены, только внутри workspace проекта.
7. **Архивариус — только расписание.** Шаг FLOW-процесса убирается; роль остаётся в БД как `deprecated` до миграции чатов и шаблонов (жёсткое удаление из `ROLE_IDS` ломает `update_role()`).
8. **Расписание:** часовой пояс — МСК. Лимита стоимости нет. Отчёты хранятся без ограничения. Частота — **ежедневно в 03:00 МСК** (`0 3 * * *`), с возможностью переопределить расписание на конкретный проект. Трассы размышления **хранятся** вместе с отчётами.
9. **Компоновку менять можно.** Откат обеспечивается бэкапами и Git; ограничение «только цвета» снимается, этап 1 может менять структуру панелей.
10. **Один владелец.** Общий `HUB_TOKEN` остаётся; многопользовательские бюджеты и аудит ролей не вводятся.

## Закрыто (было открыто)

- **Частота запуска архивариуса.** Ежедневно в 03:00 МСК; пока загрузки нет, ночной прогон наводит порядок. Отдельный проект может задать своё расписание.
- **Хранение трасс размышления.** Хранить вместе с отчётами, без ограничения срока.

## Требование к хранению отчётов архивариуса

Отчёты и трассы хранятся **по дням**, каждый подписан, чтобы их можно было найти без знания структуры каталогов:

```text
ops/archivist/
  INDEX.md                      # оглавление: дата → проект → что сделано → что предложено убрать
  2026-11-14/
    summary.md                  # человекочитаемый отчёт: что перемещено, что переименовано, что в карантине
    deletions-proposed.md        # список «что предлагаю убрать» — только предложение, файлы не трогаются
    run.json                     # машиночитаемое: проект, агент/модель, старт/финиш, длительность, токены, статус
    thinking.md                  # трасса размышления модели
```

Правила:

1. Один запуск — одна папка `<YYYY-MM-DD>` с временем в имени, если запусков в сутки несколько (`2026-11-14/031500-<project-slug>/`).
2. Каждый файл начинается с шапки: дата, проект, модель, роль, статус, длительность.
3. `INDEX.md` дополняется той же операцией, что пишет отчёт, — отдельного шага «собрать оглавление» нет.
4. Отчёты неизменяемы: исправление оформляется новым запуском, старый файл не перезаписывается.
5. Поиск по истории — по `INDEX.md` и по имени папки даты; файлы не зависят от расположения проекта.
