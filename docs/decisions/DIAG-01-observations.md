# DIAG-01 — модель наблюдений вместо флага verified

Решение от 10.11.2026. Основание: `docs/IMPLEMENTATION-BASELINE.md` §5 — все девять агентов помечены `status: verified`, но это статический флаг реестра, а не свежее наблюдение; времени, источника, TTL и разделения configured/compatibility/availability/quality нет. Пункт 1 в §7 baseline.

## Принцип

Статус агента перестаёт быть одним словом в YAML. Источник правды — набор наблюдений, каждое со своим происхождением, временем и сроком жизни. Отсутствие свежего наблюдения — это не «ок», а `unknown`.

Четыре независимых вида, не сводимых друг к другу:

| Вид | Что означает | Кто пишет | TTL по умолчанию |
|---|---|---|---|
| `configured` | карточка есть в реестре, адаптер и транспорт заданы, обязательные поля заполнены | реестр при старте | не истекает (это факт конфигурации) |
| `compatibility` | заявленные возможности подтверждены для этой версии адаптера/протокола (workdir, выбор модели, изображения) | реестр + версия адаптера | 7 суток |
| `availability` | исполнитель отвечает прямо сейчас: heartbeat, HTTP-проба, наличие CLI | воркер/probes (DIAG-02) | 3 минуты (2 интервала heartbeat) |
| `quality` | результат последних прогонов приемлем: доля успешных, время, ошибки формата | завершённые задания | 24 часа |

`quality` **не** выводится из `availability`: живой канал может стабильно отдавать мусор, и наоборот.

## Форма наблюдения

```json
{
  "kind": "availability",
  "state": "stale",
  "source": "heartbeat",
  "checked_at": "2026-11-10T01:14:00+03:00",
  "ttl_s": 180,
  "reason": "последний heartbeat 9 минут назад",
  "detail": {"version": "0.3.0", "protocol": 2}
}
```

- `state`: `ok` | `degraded` | `failed` | `unknown` | `stale`. Вычисляется на чтение, а не хранится: `checked_at + ttl_s < now` → `stale`, нет наблюдения → `unknown`.
- `reason` — человеческая причина для UI, обязательна для всего, кроме `ok`.
- `detail` — только несекретные поля; токены и ключи не попадают ни в detail, ни в лог.

## API

`GET /agents` и `GET /agent-profiles/{agent_id}` сохраняют прежние поля (обратная совместимость для текущего UI и внешних клиентов) и добавляют:

```json
{
  "id": "codex",
  "status": "verified",
  "observations": {"configured": {...}, "compatibility": {...}, "availability": {...}, "quality": {...}},
  "effective_state": "unknown"
}
```

- `status: verified` остаётся в ответе как историческое поле совместимости и **не** используется новым UI.
- `effective_state` — сводка для списка: `ok`, если `configured.ok` и `availability.ok`; `degraded`, если что-то `degraded`/`stale`, но канал работает; `failed` при `failed`; `unknown`, если нет данных о доступности. Статус хаба (`/health`) в `effective_state` не подставляется.

## UI

- Бейдж рядом с агентом: `ok` — зелёный, `degraded`/`stale` — жёлтый, `failed` — красный, `unknown` — серый с подписью «нет свежих данных».
- Раскрытие бейджа показывает четыре вида с источником, временем и причиной; для `stale` — сколько прошло с проверки.
- Пока идут только реестровые наблюдения, у всех агентов `availability: unknown`, и UI обязан показывать именно это, а не зелёный «verified».

## Совместимость и миграция

1. `config/agents.yaml`: `status: verified` → `configured: true` (плюс существующие `supports_workdir`, `model_selection`). Значение `status` в ответе API формируется из `configured`/`compatibility`, чтобы старые клиенты не сломались.
2. Схема БД: добавочная таблица `agent_observations(id, agent_id, kind, state, source, checked_at, ttl_s, reason, detail jsonb)`; реестровые наблюдения пишутся при старте, `availability` — только из heartbeat/probes.
3. Никаких удалений и переименований в существующих таблицах.

## Приёмка DIAG-01

- Свежих heartbeat нет → UI показывает `unknown`/`stale`, а не `verified`.
- `GET /agents` содержит все четыре вида наблюдений для каждого агента.
- Истёкший TTL переводит наблюдение в `stale` без записи в БД (вычисление на чтение) — проверяется тестом с подменой времени.
- Недоступный хаб не делает агентов «ok»: `/health` и `effective_state` независимы.
