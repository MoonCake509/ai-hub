# DIAG-02 — исполнитель проб: что именно проверяем и как различаем отказы

Решение от 10.11.2026. Основание: `docs/IMPLEMENTATION-BASELINE.md`, DIAG-01 (`docs/decisions/DIAG-01-observations.md`) — модель наблюдений уже есть, но писать в `availability` пока некому. Здесь только пробы: список видов, различение причин, дедупликация, дедлайны. Heartbeat воркеров с версией протокола — DIAG-03.

## Принцип

Проба отвечает на один узкий вопрос и обязана назвать причину отказа так, чтобы человек не бегал смотреть логи: «сервис не слушает», «сервис ответил 401», «ответил 200, но это не JSON», «JSON есть, нужной модели в каталоге нет», «бинарь есть, но лежит в другом месте». Пять разных состояний не должны схлопываться в одно «недоступно».

Пробы **пассивные**: только локальные HTTP, TCP и файловая система. Платных вызовов моделей нет по конструкции — в модуле нет вида пробы, который отправляет prompt. Активная проверка модели появится отдельно (Q-01/ADAPTER-01) и потребует явного разрешения.

## Виды проб

| вид | что делает | что различает |
|---|---|---|
| `http_json` | GET/POST по URL с таймаутом, разбор JSON и проверка обязательных ключей/значений | `connection` (порт закрыт/DNS), `timeout`, `auth` (401/403), `server` (5xx), `body` (200, но не JSON), `catalog` (JSON без нужного ключа/значения — «API жив, модели нет»), `ok` |
| `cli_binary` | ищет исполняемый файл по зарегистрированному пути, затем по PATH и типовым каталогам | `ok` (путь совпал), `cli_moved` (найден в другом месте — degraded), `cli_missing` (не найден) |
| `tcp_port` | TCP-connect к host:port | `ok`, `refused` (не слушает), `timeout` |

`http_json` покрывает и CDP (`/json/version` с обязательным ключом `Browser`): ответил HTTP, но без нужного ключа → `catalog`/`protocol`, то есть «порт занят другим процессом», а не «CDP работает».

## Формат результата

```json
{
  "agent_id": "xiaomi-ocr-server",
  "probe": "http_json",
  "target": "http://172.18.0.1:8787/v1/models",
  "state": "failed",
  "reason": "HTTP 200, но в ответе нет JSON",
  "detail": {"http_status": 200, "content_type": "text/html", "latency_ms": 12},
  "checked_at": "2026-11-10T06:40:00+00:00",
  "dedup_key": "http_json|http://172.18.0.1:8787/v1/models"
}
```

`reason` — человеческая формулировка, `detail` — факты без секретов: заголовок авторизации в пробе берётся из переменной окружения по имени, значение не попадает ни в detail, ни в лог (фильтр `observations._clean_detail`).

## Дедупликация и параллельность

- Ключ дедупликации — вид пробы плюс нормализованная цель (URL без query, путь бинаря, host:port). Два агента на одном адресе проверяются одним сетевым вызовом; результат копируется обоим с пометкой `deduplicated: true`.
- Параллельность ограничена: пул на 4 пробы, у каждой свой `timeout_s` (по умолчанию 5), у всего прогона — общий дедлайн 20 с; не успевшие получают `timeout` с причиной «общий дедлайн прогона».
- Повторный прогон внутри TTL доступности (180 с) не делает сетевых вызовов, если не передан `force: true`: результат берётся из `agent_observations`.

## Где задаются цели

Проверено фактом: из контейнера хаба хостовые сервисы (`127.0.0.1:8787` OCR, `:9333` CDP, `:11434` llama.cpp) по адресу шлюза TCP-соединение принимают, но HTTP-ответа нет ни из прода, ни со стенда (таймаут 8 с). Ставить такие пробы в контейнер нельзя: получится ложный `timeout` при живом сервисе. Поэтому в этой поставке пробы агентов на хосте не включаются — их выполняет воркер на самом хосте (DIAG-03, heartbeat с версией и возможностями). Сейчас проверяются сервисы, которые видит сам контейнер: `litellm` (HTTP + ключ из окружения) и `postgres` (TCP, хост берётся из `DATABASE_URL`).

### Цели агентов

`config/agents.yaml`, блок `probe` в карточке агента:

```yaml
probe:
  kind: http_json
  url: http://172.18.0.1:8787/v1/models
  timeout_s: 4
  expect:
    status: 200
    json: true
    require_keys: ["data"]
```

Адрес хоста из контейнера — `172.18.0.1` (шлюз bridge-сети, проверено: порты 8787, 9333, 11434 отвечают). Для docker-сервисов используется имя сервиса (`http://litellm:4000`).

## API

- `POST /probes/run` (токен) — прогон по всем карточкам с `probe`; тело `{"agent_id": "...", "force": true, "timeout_s": 4}` опционально. Ответ: `{"ran": n, "deduplicated": n, "results": [...]}`.
- `GET /probes/plan` (токен) — что и по каким ключам будет проверяться, без сетевых вызовов.
- `GET /probes/last` (токен) — последние результаты из памяти процесса (для отладки; источник правды — `agent_observations`).

## Приёмка

- OCR API жив/модель мертва: `http_json` различает 200+JSON без нужной модели (`catalog`) и закрытый порт (`connection`).
- CLI переместился: `cli_binary` возвращает `cli_moved` с обоими путями, а не «не найден».
- Неверная авторизация: 401/403 → `auth`, не `connection`.
- Ресурс занят: HTTP-ответ без обязательного ключа → `protocol`, причина «порт отвечает, но это не ожидаемый сервис».
- 200 с ошибочным body: `body`, причина с content-type.
- Повторный прогон в пределах TTL не делает вызовов; два агента с одним адресом дают один вызов.

## Вне DIAG-02

Платные/активные проверки модели, heartbeat с версией и возможностями (DIAG-03), история проб в UI (бейдж и причины уже показывает DIAG-01).

## Наблюдение по инфраструктуре

`config/agents.yaml`, ключ `services:` — пробы сервисов; ключ `probe:` в карточке агента остаётся поддержанным, но заполняется только там, где хаб действительно может проверить цель (например, docker-адрес), иначе воркером (DIAG-03).

Проверено на проде: `litellm:4000/v1/models` с мастер-ключом отвечает 200 и списком моделей; без ключа — 401, что классифицируется как `auth`, а не `connection`.
