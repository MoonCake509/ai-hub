# DIAG-03. Heartbeat воркера: кто исполняет, с какими возможностями и насколько свежо

**Дата:** 2026-11-10 · **Статус:** принято и реализовано

## Вопрос

Карточка агента говорила «доступен», потому что кто-то где-то отправил heartbeat попытки.
Пользователь не мог отличить исполнителя от другого SSH-пользователя, второго процесса или
устаревшего состояния. Нужно видеть: на какой машине, от какого пользователя ОС, каким
процессом и каким именно CLI выполняется агент; и что будет, если устройство выключили.

## Решение

Heartbeat — не «я жив», а **идентичность исполнителя**:

- `worker_id` (например `WIN-V76QC2G60Q1-host`, `DESKTOP-BHMJN55`), `host`, `os_user`, `pid`;
- `protocol` = 2 и `adapter_version` — версия контракта; чужая версия отвергается `409`, чтобы
  старый воркер не писал наблюдения по новым правилам;
- `agents[]` — кого обслуживает: `id`, путь CLI, версия CLI, размер и время изменения файла,
  локальная готовность (`ready`) и причина неготовности;
- `capabilities` — что умеет (workdir, вложения, outbox типа «файл»).

Хаб хранит последний heartbeat в `aihub.workers` и пишет по каждому агенту наблюдение
`availability` с источником `worker:<worker_id>`, TTL 180 с и подробностями
(исполнитель, хост, пользователь ОС, PID, протокол, путь и версия CLI).

**Правила честности**

1. `ok` ставится только когда воркер подтвердил готовность: CLI существует по
   зарегистрированному пути, порт исполнителя принимает соединение. Иначе — `degraded`
   с причиной («порт исполнителя 127.0.0.1:9333 не отвечает»), а не молчаливый `ok`.
2. Нет heartbeat дольше TTL — `stale`, и это видно в карточке и в `effective_state`.
   Выключенный ноутбук перестаёт выглядеть доступным сам, без ручной правки.
3. Псевдонимы не плодят карточки: воркер зовёт агента `openclaw`, а карточка — 
   `openclaw-laptop`; связь берётся из реестра (`bridge_agent`), а не из таблицы в коде.
4. Секреты не собираются: принимаются только поля белого списка, значения проходят через
   фильтр DIAG-01 (ключи с `token`, `secret`, `password`, `authorization`, `cookie`,
   `apikey`, `api_key` отбрасываются). В ответах API и в БД секретов нет.

## Границы

- Heartbeat подтверждает существование исполнителя и его готовность, но **не** качество
  ответов: это отдельное наблюдение `quality` (Q-01).
- Версия CLI берётся только при успешном коде возврата; если CLI не понимает `--version`,
  версия честно отсутствует, а не подменяется текстом ошибки.
- Порт проверяется TCP-соединением с таймаутом 1 с: «принимает соединение» ≠ «отвечает по
  протоколу». Глубина — предмет проб DIAG-02 (`http_json`).

## Проверено

- Юнит (в образе хаба): 29 проверок — TTL/границы, отказ по версии протокола, отказ по
  пустому `worker_id`, фильтрация секретов, псевдоним → карточка, `ready=false` → `degraded`.
- Живой контракт стенда: 33 проверки — приём heartbeat, `/workers`, детали в карточке,
  псевдоним `openclaw`→`openclaw-laptop`, `qwen`→`qwen-code`, `degraded` с причиной,
  `409` на чужой протокол, отсутствие секретов в ответах.
- Прод: два реальных воркера — серверный (`WIN-V76QC2G60Q1-host`, пользователь `user`,
  PID 12664) и ноутбучный (`DESKTOP-BHMJN55`, пользователь `lavy`, PID 4192); все 9 карточек
  получили `availability: ok` с путями CLI и версиями (Hermes 0.21.5/0.21.6, OpenClaw 2026.10.10).
- Остановка воркера проверена правилом TTL: при отсутствии heartbeat 180 с карточка
  становится `stale` (юнит + контракт).
